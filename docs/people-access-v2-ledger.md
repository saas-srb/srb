## ViralPulse failing tests: findings (2026-11-22)
- wp0 `health: scheduler states`: the TEST was stale. The Director-facing hint for an overdue scheduled job is plain language ("Ask your administrator to check that scheduled jobs are running."); it deliberately does not name `CRON_SECRET` (the secret is optional now with the Vercel-cron fallback and the product never shows environment variable names). Test updated to the plain wording.
- wp2 `sweep re-seals tokens after a key rotation`: the TEST was stale, the code is right. Rotation is a keyring operation now (`rotateKey`: a fresh root key becomes active, older versions stay decrypt-only); the environment variable only seeds the keyring the first time, so swapping `PLATFORM_ENCRYPTION_KEY` mid-run no longer rotates anything. The test now rotates through the keyring and proves, on a throwaway database: a social token sealed with the older keyring version is still readable and usable, `isSealedWithCurrentKey` is false for it, the accounts sweep re-seals it with the active key, and the secret is unchanged. Note: the keyring's own background re-seal only covers platform-level locations (`keyring/samples.ts`: 2FA secrets, platform settings, payment accounts); per-company product data (social tokens, bank details, vault credentials) is re-sealed lazily by each product's own sweep, and nothing becomes unreadable meanwhile because older versions stay available for decrypting.

## SiteCraft + DealFlow: design hazards found (not started)
- The shared Offers/Wallet/Push/Chatbot pages live physically in SiteCraft; DealFlow code does not use them. A micro feature with an "or" legacy link across products (CMS editor OR DealFlow manager) needs `derive.ts` to look legacy keys up in the product that owns them (today it reads `access[m.product]`), and `splitPicked` / `completeAccess` must not drop or leak the cross-product micro for a person who only holds one side (a CMS-only editor would otherwise lose offers access on resave, or a DealFlow-only manager would gain a SiteCraft entry role). Decide where the shared features live (recommended: where the pages are, SiteCraft) and test both one-sided people explicitly.
- Huddle: its checks take `user` objects (not a viewer) in many lib functions (`isChatAdmin(user)` in channels, search, access, route-helpers); the micro subject has to be loaded onto the Messenger user object first. Channel owner/admin roles are per-channel memberships and stay as they are.


## Cross-cutting gap found (AI agent layer)
The Ask AI / agent engine (`src/lib/ai/agent/`) decides which kinds of record and action a person is offered with a per-panel role list (`access.ts` `PANEL_ROLES`/`hasLevel`); the per-entity `allow`/`allowRead` closures are not evaluated by the engine. For every finished product I added micro-feature scopes to the main read entities and guards on report runs, and write actions go through the product's own server actions (which enforce micro features), but direct-database agent actions of products that run them without a server action are still governed by the role lists. Needs its own pass: carry the person's access subject on `AgentUser` and make `hasLevel` use it.
