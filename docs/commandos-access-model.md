# CommandOS access model (P2)

Code: `src/lib/access/`. Requirements R7, R10, R11. Owner decisions D2, D3, D4, D6 (see `docs/commandos-restructure-plan.md` section 5).

## The model

- A person has ONE `access` map: `{ productKey: { featureKey: "read" | "write" } }`. Absence means no access. Two levels only; write implies read.
- Product keys are the product slugs (`talentos`, `sprintos`, `cashflow-ai`, ...). 17 products.
- 265 features, each with a stable key `<role file>.<capability>` (for example `hrms.MANAGE_EMPLOYEES`). The catalogue (`catalogue.generated.ts`) is generated by `npm run gen:access` from the 20 `src/lib/*-roles.ts` files: one feature per legacy capability, nothing merged, so nothing a person can do today is lost or widened. Risky actions (publish, place calls, approvals, secret reveal, own-versus-all) are their own write features (D4).
- Meaning of the levels: Read = open, view, use (the capability is a view/use capability; granting Write adds nothing, so a view feature caps at Read). Write = everything Read allows plus change, create, approve, send, publish, reveal. Each feature carries `level`, the level at which the legacy capability becomes true.
- The Director (holds `super_admin`) always has write everywhere and cannot be reduced (`can()` returns true; `setAccess` refuses to change a Director).
- Self-service features (`me.tasks`, `me.leave`, `me.payslips`, `me.profile`, `me.notifications`, `me.expenses`, `me.chat`) are always on for everyone, are not in the matrix and are never stored (D3).

## API

- `can(subject, product, feature, level)` pure. `requireAccess(...)` throws `AccessDeniedError` (use at the top of server actions, route handlers, pages). `normalizeAccess(input)` cleans a map.
- `describeAccess(access, isDirector)` is the read model for the Preview step and the locked-item UI: per product, per feature the effective level (`write`, `read`, `none`), counts, whether the product is reachable; `isProductLocked(view, product)`.
- Server: `loadAccessSubject(userId)` (stored map, or what the legacy roles give today for a person who has no map yet), `setAccess(userId, map, actorId)`.

## Compatibility adapter (`adapter.ts`, `legacy.ts`)

The legacy role files are unchanged and are used as the oracle.

- `legacyToAccess(user)`: what a legacy user (roles plus permission overrides) can do, as a map. Exact.
- `accessToLegacy(map)`: the roles and permission overrides that make every legacy check (`hrmsCan`, `canManageProjects`, `hasXAccess`, `resolvePermission` ...) answer what the map says. Roles are chosen by set cover over what each role grants, overrides fix the rest, then the result is verified against the legacy functions themselves. It returns `conflicts` split into `widened` (legacy would allow more than the map: the map is refused) and `withheld` (legacy cannot express it: new code honours it, legacy checks say no). Never silent.
- `completeAccess(map)`: when a product is given any feature, the product can be opened and its baseline is written into the map. The baseline is what the product's lowest role bundles, including access the legacy code implies in other products (for example a training role implies the test-taker role). It is visible in the Preview, not hidden.
- Wiring: P3 (People & Access) calls `accessToLegacy` when it saves a person and writes the derived `roles` and `permissionOverrides` next to the map, so every product keeps reading the fields it reads today. P2 does not change any live user: the migration only ADDS `access`.

## Parity harness (`npm run test:access`)

For every role of every role file and every capability: legacy answer equals the answer from the matrix, and equals the legacy answer on the user derived back from the matrix. Result: zero differences over 2,516,970 comparisons (92 single roles, 2,758 role combinations (every pair of any two roles plus 300 random multi-role people), 1,916 override cases). The generated catalogue is checked against the role files on every run.

### Intentional differences (the only ones)

1. Hand-made maps can ask for a combination the legacy role bundles do not allow. They are detected, never silent. For the per-product presets the People & Access screen will offer: 32 of 34 (17 products x Read Only / Read & Write) are exact. The two exceptions (documented, tested): AgentOS Read Only and EvalIQ Read Only. Their lowest role also carries a manager/staff tier gate (`aibots.isAibotsManagerTier`, `ots.isOtsStaff`), so legacy checks would be wider than the map; `setAccess` refuses that map until those gates are replaced by feature checks (P8).
2. Random maps of unrelated features conflict often (23 of 150 exact in the test) because role bundles cannot be split by overrides for capabilities without an override key (about 70 of the 265). P3 must offer product-level presets and show the Preview with the implied baseline; per-feature toggles are enforced by `can()` in new code, and legacy checks follow once each product moves to `requireAccess` (P8).
3. Tier gates that are identities rather than permissions (`isXAdmin`, `isXManagerTier`, "employee only", `isSuperAdmin`) are carried unchanged for migrated people and never set by a hand-made map.

## Migration (legacy -> map)

`npm run migrate:access -- --dry-run|--apply|--revert --id <migration-id> [--company <id>]` with `MONGODB_URI` pointing at a throwaway database (the script refuses anything else). Adds `access` and `accessMigration: {id, at, source}`; skips people who already have `access`; never touches roles, overrides, custom roles or saved roles. Revert removes only what that migration wrote. Tested on a throwaway database (`scripts/test-access-flow.ts`).

## Not done yet (by design)

- No UI change (P3). No product has been moved from `xCan(...)` to `requireAccess(...)` (P8, with the unguarded list in `docs/commandos-audit.md`).
- Custom roles and designation role bundles are converted to map rows by the migration (their effect is already inside `roles` and `permissionOverrides`) and hidden in P3; nothing is deleted.

## How the People & Access screen uses it (P3)

- Step 2 shows every product and feature (`buildAccessUi`), grouped product, area, feature, with None / Read only / Read & Write. The Director's picks are `picked`; `completeWith` adds the product basics (baseline) and the Workspace basics, shown as Included and locked.
- Quick buttons per product: No access, Read only, Read & Write (everything). For AgentOS and EvalIQ the Read only button is "Read only (view and reports)" and starts from the next level up that the older roles can express exactly. For those two products that level also includes write features (listed under the button and in a note), so it is not read-only in the strict sense.
- Save (`people.ts`): `checkAccess` completes the map, `accessToLegacy` derives the older roles and overrides; a map that would widen older access is refused with a plain explanation; features the older screens cannot honour are saved and shown as "not available in every part yet". Custom roles are cleared on save (their effect is inside the derived roles). A Director's details can be edited, never their access. Delegated managers cannot save a map that needs individual overrides, and nobody edits their own access.
- Editing a person with no saved map derives it from their older roles (`prefillFromLegacy`), so nothing has to be migrated first.


## P8-C: AgentOS "Read only" is truly read only (2026-11-17)
AgentOS is finished on micro features (`src/lib/access/micro/agentos.ts`). Intentional differences from the old role model:
- "Read only" in Step 2 now grants only read-level features: open the dashboard, see agents in the Agent Hub, see calls, read the activity log. It no longer includes chatting or voice calls (`agents.use`, `calls.place` are Read & Write features, because they create conversations and calls). Step 2 shows plain "Read only", without the "next level up" wording.
- A person who can only see agents opens the hub but a typed chat address shows the polite locked page; the chat API, voice start and chat rename are refused server-side.
- "Read everyone's chats" (`chats.all`) is a scope feature and is never part of the quick Read only button. Old people keep exactly what they had (the old role bundles map to the same micro features, 0 unintended differences in `test:agentos-access`).
- Dashboard numbers span everyone for a person who holds `chats.all` or `agents.edit` (the old manager-tier rule, unchanged).
- EvalIQ still uses the older wording until it is finished the same way.
